xudo

xudo is sudo for AI agents. Your agent (Claude Code, Codex, Grok…) calls xudo where it would call sudo. It checks two things: is this an agent harness you verified on this machine, and does a rule you wrote allow this exact command with these exact arguments? If yes, it runs as root with no password prompt. If a rule says a person must decide, the command waits in the ido queue until you review and run it. Anyone else gets the normal sudo password prompt, and a command no rule allows is refused. xudo itself never asks for or handles a password. Every decision goes into a tamper-evident log.

The design, in five steps:

  1. You install one package and choose rule files: what agents may run, down to each argument.
  2. You verify a harness once (not built yet): on a server the admin registers it; on a laptop you type your sudo password once per session.
  3. The agent runs xudo exec -- <command>. A root service checks who is asking (from the kernel, not from names) and matches the command against the rules.
  4. Allowed: runs as root now, with no password (not built yet). Needs a person: waits in ido. Anyone else: the normal sudo password prompt. A command no rule allows: refused. A built-in deny-list refuses shells and other escapes whatever the rules say.
  5. Everything is recorded in a log that shows any tampering.

Beta. Not externally audited. Today's beta asks your password for every request. The passwordless agent path and Landlock confinement are not in this release. See security status and limits.

Works today. xudo exec sends your command to a root service, the broker. The broker checks it against the rules in /etc/xudo/rules.d and a built-in refusal list, and writes the decision to a hash-chained audit log. It then hands the command through sudo to a separate root program, the gate. sudo asks for the password, and the gate checks the rules again before it runs anything. Other tools: xudo check tests rule files, xudo doctor lists other ways to get root on the machine, and a daily job (Pasban) verifies the audit log.

In the code, not usable yet. A harness registry, the rule keys harness and outcome, and a root-held review queue shown by ido. They act only for a caller that the kernel places in a scope root made for a registered agent. Nothing in this release creates such a scope.

Not built yet. Agent enrolment, passwordless runs for a registered agent, rule packs, temporary permissions and an apt repository.

Install

v0.1.0-beta.2 is a pre-release. Download the .deb, SHA256SUMS, and its .cosign.bundle from the GitHub Release. GitHub shows the ~ in the Debian version as ., so verify the checksum with sed 's/~/./' SHA256SUMS | sha256sum -c --ignore-missing. Replace <ver> with the Debian version, <arch> with amd64 or arm64, and <tag> with the Git tag; for example, <ver> 0.1.0~beta.2 corresponds to <tag> v0.1.0-beta.2.

sed 's/~/./' SHA256SUMS | sha256sum -c --ignore-missing
cosign verify-blob --bundle xudo_<ver>_<arch>.deb.cosign.bundle --certificate-identity https://github.com/YaminT/xudo/.github/workflows/release.yml@refs/tags/<tag> --certificate-oidc-issuer https://token.actions.githubusercontent.com xudo_<ver>_<arch>.deb
sudo apt install ./xudo_<ver>_<arch>.deb

xudo has no curl | sh installer because a privileged shell script is difficult to inspect before execution.

Example

From a checkout, --rules ./rules applies to explain. exec ignores --rules; the broker loads root's /etc/xudo/rules.d.

xudo --rules ./rules explain -- /usr/bin/systemctl --no-pager --full status nginx.service
xudo doctor
ido queue -m "show listeners after review" -- /usr/bin/ss -tulpnH

explain reports a decision without execution. After installing the package, add your user to the xudo group with sudo usermod -aG xudo YOUR_USER, then log out and back in. This is a deliberate privilege grant: group members can invoke the privileged gate. Then run xudo exec -- /usr/bin/systemctl --no-pager --full status nginx.service; it uses the host password prompt and gate.
