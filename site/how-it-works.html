How it works

A harness calls xudo exec -- PROGRAM ARGS. The root broker identifies a verified harness from kernel-attested scope facts and a root-owned registry, then checks the exact command and arguments against policy. The root gate checks the request and policy again before execution.

  1. Allow: a matching rule lets a verified harness run the command. It runs without a password only if root has also enabled the opt-in agent path.
  2. Ask human: a matching ask-human rule puts the request in the broker's root-held queue. A separate reviewer uses ido to review and run it through the host's password path.
  3. Deny: a deny rule, missing match, compiled-in refusal, or failed check stops the request. The command does not run.

The shipped enrollment path runs a harness as its own account in a root-created systemd service scope. Enrollment grants no commands by itself. A rule must name the harness, and passwordless execution also requires the explicit sudo xudo install --agent-path opt-in (sudo or sudo-rs only). The package and plain install keep this off.

Session start and attach for a harness using a logged-in user's account are not implemented. Humans use the password-authenticated path. The optional xudo watch confirmation is an additional human-path check.

ido can read the broker's root-held queue but cannot alter it. The requesting harness cannot approve or answer its own entry. See the product source of truth and security limits.
